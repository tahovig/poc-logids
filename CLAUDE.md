# Project: poc-logids (working title)

## Goal

Second in a series of portfolio projects supporting a career pivot from software engineering to cybersecurity engineering (first: `poc-osint`, at `~/dev-projects/tah-osint-poc`). A log-based anomaly detection tool — a "mini IDS" — that parses log data (initially file-based, likely with a live-tail mode) and flags suspicious patterns. Demonstrates blue-team/detection-engineering skill, complementing `poc-osint`'s offensive/recon-leaning first project.

## Decided so far (from planning discussion in the poc-osint session, before this project existed)

- **Type: log-based, not raw packet capture.** A true real-time NIDS (live packet sniffing) was considered and rejected: packet capture needs libpcap/raw sockets + elevated privileges (root or `CAP_NET_RAW`), WSL2's NAT'd virtual networking limits what real external traffic you'd even observe (you'd mostly be capturing your own loopback/Docker traffic, which would need synthesizing anyway), and it breaks the deterministic/mockable testing philosophy that worked well for `poc-osint`. Log-based detection (auth logs, web server logs, etc.) is far more buildable and testable — feed known log lines, assert known detections, no privilege escalation, no environment-specific networking quirks. A live-tail mode (watching a growing log file, like `tail -f`) can still deliver most of the "real-time" feel without packet-capture complexity, and maps more directly to actual SOC/blue-team log-analysis work than a packet sniffer would.
- **Language: Go.** The task shape (tail log → parse → detect → alert, streaming) is a concurrency-pipeline problem, not a raw-throughput/bare-metal one. Go's goroutines/channels fit that shape naturally; it distributes as a single static binary (no venv story, a nice contrast to `poc-osint`'s Python setup); it's genuinely common in modern security tooling (Suricata's newer tooling, trivy, syft, grype); and it carries far lower project-risk/dev-time than C++ or C for equivalent portfolio payoff, since this isn't a wire-speed/bare-metal problem. C++ and C were considered but rejected on the grounds that their low-level control only pays off for packet-level processing, which was already ruled out. Rust was considered as a security-conscious systems-language alternative (increasingly the real industry choice for security tooling, since a memory-corruption bug in a security tool is a uniquely bad failure mode) but not chosen for this project — steeper learning curve, more time would go to language mechanics than detection logic. Worth remembering as a candidate for a *future* portfolio project if a systems-language/memory-safety narrative becomes the goal.

## Scope: SSH brute-force detection in auth.log

**Detection target**: repeated failed-auth attempts from a single source IP within a configurable time window, in SSH/syslog auth-log-style data (`sshd(pam_unix)[...]: authentication failure; ... rhost=<ip>` and equivalent modern OpenSSH `Failed password for ... from <ip> port ... ssh2` lines). Chosen over web-log scanning detection (repeated 4xx bursts) to keep v1 tightly scoped to one well-defined signal — same discipline as `poc-osint` shipping one narrow module well rather than two loose ones. Web-log scanning detection is documented future work, not built now.

**Log data sources** (decided after evaluating real vs. synthetic — user wanted real, non-self-generated data for the demo, not just synthetic):
- **Real demo data**: [loghub](https://github.com/logpai/loghub) `Linux` dataset — genuine production syslog from a real system, 263.9 days / 25,567 lines / 2.25 MiB, freely available for research/academic use with attribution (full dataset via Zenodo, sample at `Linux/Linux_2k.log`). Verified via direct fetch: contains real SSH brute-force patterns (e.g. dozens of `authentication failure; ... rhost=218.188.2.4` from one IP within the same second). Two other real-data options were considered and set aside for now: standing up a real internet-facing SSH honeypot/VPS (more authentic, mirrors `poc-osint`'s live-testing approach, but costs money and needs days to accumulate a sample — a candidate stretch goal later) and other public honeypot datasets.
- **Test/CI fixtures**: synthetic generated log lines, deterministic, no live dependency — same philosophy as `poc-osint`'s Docker fixtures.

**Explicitly deferred — not part of this project**: DNP3/ICS-SCADA log or protocol analysis. User has a strong background in critical infrastructure protection (energy generation/transmission/distribution, EMS) and raised DNP3 detection as a possible angle, using public pcap datasets (e.g. Netresec's 4SICS ICS lab captures). Correctly self-identified as a poor fit here: DNP3 analysis is pcap-native, and this project's whole premise (see "Decided so far" above) is log-based specifically to avoid packet-capture complexity. A technical bridge exists (Zeek's DNP3 analyzer converts pcap → structured `dnp3.log`), but folding it in as a secondary format would dilute both this project's focus and the ICS angle's own value. Flagged as a strong candidate for one of the "2-3 more POC projects" mentioned in the `poc-osint` Goal section — deserves to be its own pcap-native project built around the EMS background as the headline, not a footnote here.

**Live-tail mechanism**: `fsnotify`-based file watching, not polling. Event-driven, handles log rotation/truncation (real auth.log gets rotated by logrotate) better than a naive poll loop, and is the standard approach Go tail implementations use (e.g. patterns from `nxadm/tail`). One added dependency, well-maintained. Rotation-handling behavior should be documented explicitly in the README once built — a legitimate engineering-rigor point, similar to how `poc-osint` documented its crt.sh Postgres fallback.

**CLI framework**: stdlib `flag`, not `cobra` — decided provisionally, to revisit only if the tool ends up needing real subcommands (e.g. `scan` vs. `tail` vs. a future `compare`, mirroring `poc-osint`'s subcommand shape). Starting minimal-dependency, consistent with `poc-osint`'s style.

## Package skeleton — built

Go toolchain: installed Go 1.26.5 from the official tarball to `~/.local/go` (Ubuntu 20.04's `apt` only offers a stale `golang-go 1.13`), added to `PATH` via `~/.bashrc`. No `sudo` available non-interactively in this environment, so it's a user-local install rather than `/usr/local/go`.

**Module layout** — deviated from `poc-osint`'s `code/`-nested src-layout: Go's convention is `go.mod` at the repo root (every Go tool assumes this), so `code/` was dropped as a source container; `resources/` still holds non-code material. Module path `github.com/tahovig/poc-logids`, no external dependencies yet (added once `fsnotify`-based live-tail is built).

- `cmd/poc-logids/main.go` — CLI entry point. Flags: `-file` (required), `-json`, `-threshold` (default 5), `-window` (default 60s, Go duration syntax). Reads the file with a buffered line scanner, parses, detects, renders. Bad/missing `-file` produces a clean stderr message + usage + exit 1, not a panic.
- `internal/parser/parser.go` — `ParseLine(line string) (AuthFailureEvent, bool)`, pure/no I/O. Two regex formats tried in order: the older `sshd(pam_unix)[pid]: authentication failure; ... rhost=<host>` syslog format (needed for the loghub dataset — `rhost` may be a raw IP or a reverse-DNS hostname, `user=` only present on some lines) and the modern OpenSSH `sshd[pid]: Failed password for (invalid user )?<user> from <ip> port <port> ssh2` format. `ok` is `false` for the many unrelated lines in a real auth log (session open/close, cron, logrotate, the `pam_unix` "check pass; user unknown" precursor line that has no `rhost` and would double-count if matched) — not an error. Syslog timestamps have no year (`Jan _2 15:04:05` layout, parses into year 0000); detection only relies on relative deltas within one log, so this is an accepted, documented limitation, not a bug — would need real handling before ingesting logs spanning a Dec 31 → Jan 1 boundary.
- `internal/detector/detector.go` — `Detect(events, Config{Threshold, Window}) []Alert`. Groups by source, sorts by timestamp, then chains consecutive attempts into a burst as long as each gap stays within `Window`; a chain flagged if its length reaches `Threshold`. **Bug found via real-data verification, fixed**: an earlier sliding-window version capped each alert at exactly `Threshold` events and restarted the window immediately after crossing it, which fragmented one real 10-attempt burst (loghub data, syslog's 1-second timestamp resolution means several attempts often land on the same second) into two artificial 5-attempt alerts. Rewritten to chain-until-the-burst-actually-ends instead of capping at threshold; regression test (`TestDetect_LongBurstNotFragmented`) added. `DefaultConfig` is 5 attempts / 60s.
- `internal/output/output.go` — `ToJSON` (indented `encoding/json`) and `ToTable` (column-width-aligned ASCII table, `SOURCE | ATTEMPTS | FIRST SEEN | LAST SEEN | USERS TRIED`) — the terminal/ASCII visualization preference applied from the start rather than retrofitted.
- 18 tests across all three packages (table-driven), `go vet` clean, all real fixture lines in `parser_test.go` are taken verbatim from the real loghub sample, not invented.
- **Verified end-to-end against real data**: built the binary and ran it against `resources/loghub-linux/Linux_2k.log` (real production syslog, not synthetic) — 41 genuine brute-force bursts detected at default thresholds, table and `-json` output both confirmed, missing-`-file` error path confirmed. This run is what surfaced the burst-fragmentation bug above.
- `resources/loghub-linux/Linux_2k.log` — vendored real loghub sample (2,000 lines) + `README.md` noting source/license/fetch date, per the data-source decision above.

## Live-tail mode — built

Added `github.com/fsnotify/fsnotify` (only external dependency so far) and a new `-follow` flag.

- `internal/tail/tail.go` — `Follow(ctx, path, startOffset) (<-chan Line, error)`. Watches the file's parent directory (not the file itself — needed to see rename/create events across rotation) and filters to the target filename. A `follower` tracks read progress via an explicit `pos`/`pending` byte buffer (not a `bufio.Reader`, to avoid the seek-vs-internal-buffer inconsistency that comes from seeking backward under a `bufio.Reader`). Rotation handling:
  - **Rename/remove** (the common logrotate strategy — move old file aside, create a fresh one at the same path): closes the stale handle and retries opening the path every 100ms (`waitForReopen`) until the new file appears.
  - **In-place truncation** (`copytruncate`): detected primarily via `size < pos`, but that alone isn't sufficient — see the bug below.
  - `main.go`'s initial one-shot scan reports the exact byte offset it stopped at (via `f.Seek(0, io.SeekCurrent)` right after the scan loop, which reflects true bytes-consumed with no race against subsequent appends), and `-follow` resumes `Follow` from exactly that offset, so there's no gap or overlap between the historical scan and live watching.
- **Real bug found via a flaky test, not code review — fixed**: a bare `size < pos` check for in-place truncation missed the case where a truncate is immediately followed by a rewrite that grows the file past the old `pos` before the watcher's next check — the file never appears smaller, even though everything at and before `pos` is now different content. Reproduced this ~50% of the time with a synthetic truncate-then-immediately-rewrite test (`TestFollow_InPlaceTruncation`), confirmed it wasn't a fluke by running it 10-20x. Fixed with a bounded trailing-content check (`contentChanged`, `tailVerifyBytes = 4096`): re-verify that the bytes on disk just before `pos` still match what was last read there, re-seeding that verification window from disk whenever a follower starts at a nonzero offset (a second, related bug — a freshly created follower had an empty verification window even when `pos` was nonzero, since it never itself read the bytes before that point) or reopens after rotation. Stress-tested 20x clean after the fix. This class of race is a known, documented inherent limitation of the `copytruncate` rotation strategy generally (logrotate's own manpage admits it can lose a few lines) — the rename+recreate strategy this tool also handles has no such race.
- `internal/detector/live.go` — `Live`, a streaming counterpart to the batch `Detect`. Alerts the instant a per-source chain first reaches `Threshold`, rather than waiting for the whole burst to end (batch mode's approach) — appropriate for real-time monitoring, since waiting for an attacker to stop attacking before reporting them defeats the point. Exactly one alert per chain, not re-alerted as it keeps growing.
- `internal/output/output.go` — added `ToLine` (one-line human-readable alert, `[ALERT] <time> source=<x> attempts=<n> users=<a,b>`) and `ToJSONLine` (compact single-object JSON, "JSON lines" style — each line independently valid JSON, composable with `jq` per line) for `-follow`'s one-alert-at-a-time output, distinct from batch mode's full table/JSON-array. Also fixed `ToJSON([])`/`ToJSON(nil)` rendering as `null` instead of `[]`, caught while manually verifying JSON `-follow` output end-to-end.
- `cmd/poc-logids/main.go` — `runFollow()` uses `signal.NotifyContext` for graceful Ctrl+C/SIGTERM shutdown (prints "Stopped watching." to stderr, clean exit).
- 33 tests total (`internal/tail` adds 5, covering plain append, a partial line held across two writes, rename-based rotation, in-place truncation, and context-cancel shutdown). `gofmt`/`go vet` clean.
- **Verified end-to-end for real** (not just unit tests): built the binary, ran it with `-follow` against a real scratch log file in the background, appended a genuine 3-line burst from one IP and confirmed the `[ALERT]` line appeared live; renamed the file away and created a fresh one mid-run (simulating real logrotate) and confirmed a new burst on the rotated-to file was still caught; sent a real `SIGINT` and confirmed the graceful "Stopped watching." shutdown; separately verified `-follow -json` produces one compact JSON object per line. One append-burst test run initially showed no alert — turned out to be a bug in the *test script's* timestamp formatting (`15:20:0201`, embedding a 3-digit pid into the seconds field), not the tool; corrected and reconfirmed.

## Full loghub dataset swapped in, year-inference fixed first

Decided to swap the vendored 2k-line sample for the full loghub Linux dataset (263.9 days, 25,567 lines, 2.25 MiB — confirmed real via a direct Zenodo download, `https://zenodo.org/records/8196385/files/Linux.tar.gz?download=1`, HTTP 200, contents match the stated size/line count exactly). Trivial to vendor (232KB compressed).

**Investigation before swapping**: the full dataset genuinely crosses a calendar year boundary (file order is strictly `Jun→Jul→...→Dec→Jan→Feb`, one clean wrap) — directly exercising the year-less-timestamp limitation that had only ever been a documented theoretical concern (the 2k sample spans ~6 weeks, no wraparound). Checked how bad it was concretely before deciding anything: no source IP had activity within a week of the actual Dec 31/Jan 1 boundary (a real ~1-week logging gap over that period in this specific file), so the *first* run against the full dataset (before fixing anything) didn't corrupt detection — its only symptom was cosmetic (January alerts sorting before June ones, since both parsed to year 0000). Reported this clearly to the user rather than silently picking a path.

**User's call**: swap in the full dataset, but fix year-inference properly first rather than ship with a known-but-dormant bug just because this particular file happens not to trigger the worst case.

**`internal/parser` reworked from a stateless free function to a stateful `Parser`** (`NewParser()` + `(p *Parser) ParseLine(...)`, replacing the old package-level `ParseLine`): standard syslog year-inference heuristic — process lines in file/stream order (true of any real append-only log), increment an internal year counter whenever a line's month is earlier than the previous line's month (only a genuine Dec→Jan wrap can trigger this; ordinary jitter/interleaving never spans a full month). First line anchors year 0 — an explicit placeholder, not a real calendar year, since classic syslog format simply doesn't carry that information; display formatting never shows the year anyway, only JSON output does (as the placeholder integer).

Because year-inference depends on state carried across the whole stream, **one `Parser` instance must be reused end-to-end**: `cmd/poc-logids/main.go`'s `scanFile` now takes a `*parser.Parser` instead of calling a free function, and `main()` passes that *same* parser into `runFollow` for `-follow`, so year-tracking continuity holds across the batch-scan-to-live-tail transition rather than resetting.

3 new tests (`TestParser_YearIncrementsOnDecToJanWrap` — asserts the gap across a real wrap computes as ~4s, not ~-364 days, which is the actual point; `TestParser_NoWrapWithinSameYear`; `TestParser_MultipleWraps`). 30 tests total now.

**Verified end-to-end against the real full dataset**: before the fix, alerts list started with `Jan 7` (wrong — file starts in June). After the fix, rebuilt and reran — alerts correctly start with `Jun 11`, and `-json` output shows two consecutive placeholder years (`0000` then `0001`) spanning the wrap. Same 327 total alerts before and after (expected, confirms the fix corrected *ordering* without changing *detection* — consistent with the earlier finding that no real chain in this file straddles the boundary).

`resources/loghub-linux/Linux_2k.log` replaced with `Linux.log` (full dataset); `resources/loghub-linux/README.md` and the main README's example output updated to match (using real captured output from the full-dataset run, not fabricated).

## Severity-based visual triage — built

User feedback after running against the real full dataset: the table output was "fine" but nothing stood out for a human reviewing it — every row competed for equal attention. Presented 4 concrete mockup options via `AskUserQuestion` previews (severity color + worst-first sort; intensity bar column; summary banner; severity icon column) rather than just picking one — this is an aesthetic/UX call that's genuinely the user's to make. User picked **severity color + worst-first sort**.

- **`internal/detector.Severity`** (`SeverityNormal`/`SeverityWarning`/`SeverityCritical`) added as a field on `Alert`, computed by `severity(attempts, threshold)`: critical at ≥4x `Threshold`, warning at ≥2x, normal below that. Deliberately scaled off the *configured* `Threshold` rather than a fixed attempt count or an absolute rate — a hardcoded number would be meaningless across different `-threshold` settings, while multiples-of-threshold stays meaningful regardless. `buildAlert` now takes `threshold` to compute this; both call sites (`detectBursts`, `Live.Feed`) pass `cfg.Threshold`/`l.cfg.Threshold` through.
  - **Known, intentional gap**: `Live.Feed` always alerts at exactly `Threshold` attempts (that's the point — report the instant it's crossed, not after), so live alerts always carry `SeverityNormal`. `Detect`'s batch alerts can run well past `Threshold` before a chain breaks, so severity is meaningful there. Documented in code and tests (`TestLive_AlertsExactlyOnceAtThreshold` asserts this explicitly) rather than left as a silent surprise.
- **`internal/output`**: added a `RATE` column (attempts/minute, `internal/output.rate()`) alongside the raw count — a fast burst is a stronger signal than a slow one at the same attempt count. Duration is floored at 1 second to avoid dividing by zero when syslog's 1-second timestamp resolution puts an entire burst in the same second (real data hits this constantly). Table rows now sort worst-first (`sortedForDisplay` — severity tier, then attempts, descending) via a **copy** of the input slice — `ToJSON` deliberately keeps the original chronological order, since machine consumption wants a stable/predictable order, not visual triage. Color (ANSI red/yellow, reset after each colored row) applied via `isTerminal(os.Stdout)` — a `os.ModeCharDevice` stat check, not a new dependency (`golang.org/x/term` was the obvious alternative but wasn't needed) — same pattern as `poc-osint`'s spinner never animating into piped output. `ToLine` (the `-follow` one-liner) got the same treatment: rate field added, colored by severity.
- 9 new tests (5 detector: severity-scaling table test across different thresholds, alert-carries-severity, live-always-normal; 4 output: color-only-when-enabled, normal-never-colored, worst-first-sort-doesn't-mutate-input, line-coloring). 39 tests total.

## Real honeypot deployment — droplet up, hardened, `-follow` running as a service

Follow-up to the earlier data-source discussion (see "Scope" above), where a real internet-facing SSH box was set aside as a stretch goal in favor of the loghub dataset. Revisited once the user reviewed real detection output and wanted to watch live activity accumulate over days, not just analyze a static file.

**Infra**: DigitalOcean droplet `poc-logids-honeypot` (ID `585582241`), `45.55.223.105`, NYC3, `s-1vcpu-512mb-10gb` (~$4/mo), Ubuntu 22.04. Created via `doctl` (installed to `~/.local/bin`, no `sudo` needed — same user-local pattern as the Go toolchain install). Dedicated SSH key `~/.ssh/poc-logids-honeypot` (not the pre-existing `id_rsa` — don't reuse keys across systems).

**Note on the API token**: user pasted the DigitalOcean API token directly into chat. Used it to auth `doctl`, but flagged that a token which has touched a chat transcript should be treated as exposed and rotated (revoke + regenerate) once setup is done, per DigitalOcean's own guidance — not yet confirmed done, worth checking next session.

**Hardening applied** (script written to the scratchpad dir — NOT `/tmp` directly, which the permission classifier blocked; scratchpad worked fine):
- Non-root sudo user `poclogids` created, password locked (`passwd -l`, matches root's own already-locked-by-default state on DO images), passwordless `sudo` via `/etc/sudoers.d/poclogids` (necessary since there's no password to authenticate sudo with otherwise — same pattern cloud-init uses for default users), `adm` group membership so it can read `/var/log/auth.log` without root.
- `sshd_config`: `PermitRootLogin prohibit-password` (root stays key-only), `PasswordAuthentication yes` **kept on deliberately** — this is what makes bots' password attempts actually produce "Failed password for ..." log lines; disabling it would silence the exact signal the honeypot exists to capture.
- `ufw`: only `22/tcp` (v4 and v6) allowed, enabled.
- `unattended-upgrades`: already present on the DO image, confirmed enabled.
- Deliberately no fail2ban (per the original spec) — would ban attacker IPs after a few failures, cutting short the bursts we want to observe; safe to skip since no account has a usable password for anything to actually win.
- Verified end-to-end: SSH'd in as `poclogids` with the dedicated key, confirmed passwordless `sudo`, confirmed `adm` group read access to `/var/log/auth.log`.

**Deployment**: cross-compiled locally (`GOOS=linux GOARCH=amd64 go build`), `scp`'d to the droplet (build artifact never committed — built directly into the repo root once by mistake, immediately `rm`'d rather than risking a stray `git add -A` picking it up). Runs as a systemd service (`/etc/systemd/system/poc-logids.service`, `User=poclogids`, `Restart=on-failure`, `-file /var/log/auth.log -follow -json -quiet-startup`), `StandardOutput`/`StandardError` appended to `/home/poclogids/poc-logids-alerts.jsonl` / `poc-logids.log`. Enabled (survives reboot) and active, confirmed via `systemctl is-enabled`/`is-active`.

**Found a real bug via smoke-testing before trusting it to run unattended for days**: did an honest end-to-end test first — appended 5 synthetic lines to the *real* `/var/log/auth.log` (using the TEST-NET-3 documentation IP range, `203.0.113.7`, so they're unambiguously not real traffic) and confirmed the running service's `fsnotify` watch, `Live` detector, and JSON output all fired correctly within ~2s. That test surfaced a genuine design gap: `-follow` always does a full batch scan and prints it *before* going live -- correct for an interactive one-shot run, but wrong for a persistent service, since every restart (crash, reboot, `Restart=on-failure`) would re-scan the entire growing file from byte 0 and re-print every previously-seen alert into the same appended JSON-lines file, duplicating history each time it restarts. Fixed with a new `-quiet-startup` flag (suppresses only the initial batch *print*, not the scan itself -- offset/year-inference state still computed correctly) rather than shipping the known gap. Verified locally (a 5-line synthetic burst printed without the flag, silently suppressed with it) before redeploying. Synthetic test lines removed from the real `/var/log/auth.log` afterward (`sed` targeting the distinctive test IP only) and the alert/log files cleared, so the box starts clean for real data.

**Operational note discovered along the way**: systemd's `StandardOutput=append:PATH` creates the target file as root (before dropping to `User=poclogids`), so the file ends up `root:root` — the service can still write to it (inherits the already-open fd), but the `poclogids` user can't truncate/delete it directly without `sudo`. Not a problem, just something to remember if managing those files by hand later.

## DigitalOcean token rotation — done, but genuinely messy

Worth documenting in detail since it took several wrong turns and produced a real lesson about this environment, not just a routine credential swap.

**What happened**: the original token (pasted directly in chat during initial setup) needed rotating. First attempt: user ran `doctl auth init` via the `!` prefix (routes a command into the user's real shell). It reported success ("Using token for context default... Validating token ✔") with no visible prompt. Assumed this meant a fresh interactive prompt had been answered — **wrong assumption, not verified**. User later confirmed no prompt appeared and nothing was typed. A hash comparison (SHA-256 of the stored token vs. the originally-pasted one, compared without ever printing either raw value) was run to check — first attempt at this had a bug and wrongly showed "different" (false confidence, stated as fact without enough scrutiny); redone carefully with explicit variables, it showed **identical** — `doctl auth init` bare had just silently reused the existing valid `default` context rather than prompting, exactly matching the user's report.

**Second attempt**: tried `doctl auth init --context poclogids-v2 -t <token>` via `!`, reasoning the explicit flag would avoid needing an interactive prompt. Two problems: (a) it failed outright with `Error: Unable to read DigitalOcean access token: unknown terminal` -- the `!`-relay environment apparently doesn't provide something `doctl auth init` needs even with `-t` supplied; (b) more importantly, **the `!` prefix echoes the full command including embedded arguments back into the conversation** -- so the new token in `-t <token>` was exposed in the transcript just as directly as the original had been, despite the explicit intent to avoid exactly that. Command-line flags are not a safe way to hand a secret through `!`; only genuine interactive prompting (secret never appears as part of the relayed command) avoids this, and that path was the one failing.

**Fix**: abandoned the `!` relay entirely for this. Had the user run `doctl auth init --context poclogids-rotated` (bare, no `-t`) in a real, separate terminal window -- not routed through Claude Code at all. A brand-new, never-used context name has nothing to silently reuse, so it was guaranteed to prompt genuinely -- confirmed via screenshot (masked dot-echoed input, real "Enter your access token:" prompt). Also confirmed pasting didn't work in that prompt (had to type it) -- a real, standard-terminal-only constraint worth remembering for any future secret entry in this environment.

**Final verification**: after switching to the new context (`doctl auth switch --context poclogids-rotated`), a repeat file-based hash check gave a **confusing, contradictory result** (stored token still hashed identical to the original) that didn't square with the switch having reported success. Rather than keep trusting ad-hoc YAML parsing of `doctl`'s config (its schema has more structure -- `auth-contexts:`, a top-level `context:` pointer -- than a flat `grep` reliably resolves), switched to a **live functional test** instead: had the user revoke the original token in the dashboard, then immediately ran `doctl account get` / `doctl compute droplet list`. Both succeeded -- definitive, unambiguous proof the new context is using a genuinely different, valid token, regardless of what the file parsing seemed to show. The second (`-t`-flag, also-exposed) token from the failed attempt was never successfully applied anywhere, but is also being revoked since it touched the transcript.

**Lesson for future secret handling in this environment**: the `!` prefix is *not* automatically secret-safe. It protects a value typed in response to a genuine interactive prompt (the value itself is never part of any relayed command or output), but does *not* protect a value passed as a command-line argument (the whole command, including embedded secrets, gets echoed back). When a secret must be entered, prefer a fully separate terminal outside Claude Code entirely over the `!` relay, and verify claims about credential state with a live functional test (does a real API call succeed/fail) rather than trusting file-parsing or command output alone -- this whole saga started from an unverified assumption stated as fact.

## Honeypot silently broken for ~3 days, found and fixed

User checked in on 2026-07-20 (three days after deployment) with `grep -c "Failed password\|authentication failure" /var/log/auth.log` on the droplet — result: `0`. Investigated rather than assuming "no traffic yet"; the box was in fact being scanned constantly (6+ distinct IPs/hour in journald), but two independent, stacked bugs hid all of it from both `auth.log` and `poc-logids`.

**Bug 1 — `PasswordAuthentication no` silently overrode the deliberate `yes`.** Ubuntu's stock cloud image ships `/etc/ssh/sshd_config.d/60-cloudimg-settings.conf` with `PasswordAuthentication no`. `sshd_config`'s `Include /etc/ssh/sshd_config.d/*.conf` sits near the top of the file, and sshd resolves each directive to its *first* encountered value — so that stock drop-in beat the hardening script's `PasswordAuthentication yes` further down the main file, even though the main file still visibly said `yes`. Net effect: bots were never offered a password prompt, so **zero real "Failed password" lines had ever been generated** — confirmed by grepping the full recovered history (below): 0 real hits, only the leftover synthetic `203.0.113.7` test lines from the original smoke test. This had likely been broken since day one, not just since the reboot; the earlier "kept on deliberately" hardening note (see "Real honeypot deployment" above) was correct in intent but never actually took effect. Fixed with a new drop-in, `/etc/ssh/sshd_config.d/10-poclogids.conf` (sorts before `50-`/`60-`, so it's read first and wins) containing `PasswordAuthentication yes`. Verified before and after with `sudo sshd -T | grep -i passwordauthentication` (the authoritative *effective* config, not just grepping the file for the setting).

**Bug 2 — `/var/log/auth.log` had been an orphaned, deleted inode since 2026-07-18 06:58.** `rsyslogd` (pid unchanged since boot) still held the file open by file descriptor, but the path had been replaced out from under it — almost certainly by the `sed -i` used during the original deployment's cleanup step to strip the synthetic test lines (see "Real honeypot deployment" above). `sed -i` creates-and-renames rather than truncating in place, which orphans any process that already has the file open. Every real log line since then (8,694 lines over ~3 days) went into the invisible deleted inode instead of the path `poc-logids -follow` watches — confirmed via `sudo ls -la /proc/<rsyslog-pid>/fd`, which showed `/var/log/auth.log (deleted)`. The hidden history was recovered first (`sudo cp /proc/<pid>/fd/<n> /home/poclogids/auth.log.ghost-recovered-20260720`, ~1MB) before fixing anything, so nothing was lost. Fixed with `sudo systemctl restart rsyslog`, which released the stale fd; a `logger` test line and the SSH session's own login both landed at the real path immediately afterward, confirmed live.

**Verified end-to-end after both fixes**: within ~45 minutes, `auth.log` had 1,246 real `Failed password`/`authentication failure` lines from genuine scanner IPs, in both formats the parser targets, and `poc-logids-alerts.jsonl` had 9 real brute-force alerts (real source IPs, real usernames like `admin2`, `azureuser`, `backup`). The honeypot is now genuinely producing the signal it was built to capture.

**Lesson**: never edit a log file a running daemon has open using `sed -i` (or any create+rename edit) — it silently orphans the daemon's file descriptor. Use `truncate` or in-place `tee` instead. Also: when a monitored source looks unexpectedly quiet, verify with the *effective* runtime state (`sshd -T`, `/proc/<pid>/fd`) rather than trusting a file grep or a documented intention at face value — same category of lesson as the DigitalOcean token rotation saga above.

## Human-readable `-summary` mode — built

Follow-up to reviewing real honeypot output: the table/JSON are fine for a technical reader but assume one. User wants a mode a non-analyst could read directly, plus a reverse-DNS name alongside the raw source IP where one resolves.

**Design discussed first, then built** (per the exploratory-question norm — 2-3 sentences of tradeoff before implementing): proposed a new mode alongside the table/JSON rather than replacing them, grouped by severity into an outline with one plain-English sentence per source, capped per tier with a rollup line for the rest rather than one sentence per alert regardless of scale (the real full-dataset run has 327 alerts — a paragraph each would be worse than the table it's meant to improve on).

- **`internal/output.ToSummary`/`ToSummaryLine`** (`internal/output/output.go`): batch and single-alert (for `-follow`) variants, mirroring the existing `ToTable`/`ToLine` split. Alerts grouped into three plain-language tiers (`Severe attacks` / `Moderate attacks` / `Minor attempts`, mapped from `detector.Severity` — deliberately avoiding the "critical/warning/normal" jargon for this audience), worst-first, each capped at `summaryDetailCap` (5) alerts with a full sentence (source, attempts, users targeted, duration, rate, last-seen) before the remainder of that tier collapses into one rollup line naming the most-targeted usernames (`topUsers`) instead of being omitted or dumped in full.
- **Reverse-DNS lookup** (the "ip name lookup" ask): `resolveHostnames` runs `net.DefaultResolver.LookupAddr` concurrently, each bounded by a 1.5s timeout, and **only for the alerts that will actually get a detailed sentence** — not the rolled-up remainder — since resolving hundreds of IPs just to discard most of them would add latency for no visible benefit. A missing/timed-out PTR record is silently omitted (bare IP shown), not treated as an error. `lookupAddr` is a package-level var (not a direct call) specifically so tests substitute a stub — no live DNS in the test suite, consistent with the project's deterministic/mockable testing philosophy; real end-to-end resolution was verified separately by actually running `-summary` against the full loghub dataset (below).
- **`cmd/poc-logids/main.go`**: new `-summary` flag, mutually exclusive with `-json` (checked explicitly at startup, clean error + usage + exit 1 rather than silently picking one). `printAlerts`/`printLiveAlert` now switch across three modes (json/summary/table or json/summary/line) instead of two.
- 15 new tests in `internal/output` (tier grouping/ordering, detail-cap + rollup math, hostname included/omitted, `describeUsers`/`humanDuration`/`topUsers` table-driven cases, `seenRange` not assuming sorted input, stubbed-resolver tests for both `resolveHostnames` and `ToSummaryLine`). `go test -race` clean on the concurrent lookup code. 54 tests total.
- **Verified end-to-end against real data**: ran `-summary` against the full loghub dataset — real reverse-DNS names resolved for several live hosts (`plateautel.net`, `vision-xxl.com`, etc.), tier counts and rollup lines matched the underlying alert counts, completed quickly despite live network calls (bounded to ≤15 lookups by the cap, run concurrently). Also verified `-follow -summary` live: appended a synthetic 3-attempt burst to a scratch file and confirmed a real-time plain-English `[alert]` sentence printed (no hostname shown for the unresolvable TEST-NET-2 address used, as expected — bare IP fallback confirmed working, not just designed).

## Parser correctness bug found from real honeypot data — rsyslog message-repeated collapsing

User shared a fresh honeypot capture on 2026-07-20 (`grep -c` up to 4,347, growing well from the fix above). Reviewing it surfaced a third, independent, and more serious bug: **Ubuntu's stock rsyslog default (`$RepeatedMsgReduction on`, confirmed in `/etc/rsyslog.conf`) collapses consecutive identical log lines**, so when sshd logs the identical `Failed password for X from Y port Z ssh2` line more than once in the same connection, rsyslog writes the first occurrence and then a single summary line — `message repeated N times: [ <line> ]` — for the rest. The parser didn't recognize that format at all, so those attempts were **silently invisible**, not just miscounted.

Confirmed concretely against a real captured burst: PAM's own log confirmed 5 real failed attempts for `45.148.10.152` against `root` (`PAM 4 more authentication failures... ignoring max retries; 5 > 3`), but running it through the actual parser (a throwaway in-module script, not guesswork) showed only 1 of the 5 was counted — the other 4 were hidden inside one `message repeated 4 times: [...]` line. At the default `-threshold 5`, that entire real attack would have been missed. Quantified scope on the live droplet log: 11 such collapsed lines hiding 44 real attempts. This isn't honeypot-specific — `$RepeatedMsgReduction on` is Ubuntu's stock default, so any real-world Ubuntu `auth.log` has the same blind spot, making this a core parser correctness issue, not an infra one.

**Fix**: `internal/parser.ParseLine` signature changed from `(AuthFailureEvent, bool)` to `([]AuthFailureEvent, bool)` — a single log line can now legitimately represent more than one real event. A new `repeatedRe` matches rsyslog's `message repeated N times: [ <inner> ]` wrapper; `parseRepeated` re-parses `<inner>` against new body-only variants of the existing formats (`pamUnixBodyRe`, `openSSHBodyRe` — kept separate from the existing, already-tested `pamUnixRe`/`openSSHRe` rather than refactored into them, so real-data-verified regexes stay untouched) and synthesizes N events. All N share one timestamp (rsyslog only preserves the summary line's own time, not each individual occurrence's) — a documented, unavoidable precision loss, accepted because the alternative (not expanding) silently drops real attempts entirely, which is strictly worse for detection. Both call sites (`scanFile`'s batch loop, `runFollow`'s live loop) updated to iterate the returned slice instead of assuming one event per line.

4 new tests in `internal/parser` (including `TestParseLine_MessageRepeated_ExpandsToNEvents`, built from the real captured line above rather than an invented one, matching the project's real-fixture-data convention), plus the existing `TestParseLine` and year-inference tests updated for the new slice-returning signature. Verified end-to-end: rebuilt the binary, fed it a minimal real-derived fixture reproducing the exact burst, confirmed it now reports `ATTEMPTS: 5` (previously invisible below threshold), `go test -race ./...` clean, and reran the full vendored loghub dataset to confirm nothing regressed.

## Passive counter-intelligence enrichment (`-cti`) — built

Follow-up to reviewing a real capture showing the same source IP (`195.178.110.217`) hitting the honeypot repeatedly. User wanted to "spin up responsive probing" for repeat/severe sources — raised a real distinction before building anything: **active probing** (port-scanning or connecting to the attacker's own host) is sending unsolicited traffic to a system we don't own or have authorization to test, the "hack back" problem, generally illegal and against industry guidance regardless of provocation. **Passive enrichment** (querying third-party public registries *about* the IP, no packets sent to it) is legal and low-risk — same category as the existing reverse-DNS lookup in `-summary`. Recommended and built the passive version. User chose keyless sources only (RDAP + ip-api.com) over also adding AbuseIPDB (needs a provisioned API key/secret — a data-source/cost decision, asked rather than decided-and-stated, per [[feedback_scoping_autonomy]]).

- **New package `internal/counterintel`**: `Tracker` decides when a source has earned a lookup; `Enrich` performs it via `rdap.org` (IANA bootstrap redirector → correct RIR, network/org ownership) and `ip-api.com` (keyless free tier, GeoIP + ASN/ISP) — both HTTP calls, package-level vars (`rdapFetch`/`geoFetch`) so tests stub them, no live network in the test suite.
- **Real design gap found before shipping, not after**: the first cut triggered the repeat-offender check off `detector.Alert`s. Re-examined against the actual motivating screenshot — three single-attempt connections from one IP, ~90 seconds apart — and realized that pattern never crosses `Detect`/`Live`'s own burst threshold (5 attempts/60s default), so **no `Alert` is ever produced for it**; the repeat trigger would have silently never fired on the exact case that motivated the feature. Fixed by driving the repeat-offender signal off individual parsed events (`Tracker.ObserveEvent`, every failed-auth attempt, not just ones that end up part of an alerted burst) instead, while keeping a separate severity-based trigger (`Tracker.ObserveAlert`, fires on `SeverityCritical`) that necessarily still needs an `Alert` since only alerts carry `Severity`. Both share one cooldown map so either path suppresses the other correctly.
- **Trigger config** (`Config`/`DefaultConfig`): `RepeatThreshold` (default 3) failed-auth events from the same source within `RepeatWindow` (default 1h), *or* any single `SeverityCritical` alert, fires enrichment; `Cooldown` (default 24h) prevents re-enriching the same source repeatedly. All windowing/cooldown math uses each event/alert's own timestamp, not wall-clock time — consistent with the rest of the project (detection already relies on log-timestamp deltas), so replaying a batch file behaves the same as watching it live.
- **CLI**: `-cti` (off by default — makes outbound HTTP calls), `-cti-threshold`, `-cti-window`, `-cti-cooldown`. Wired into both paths: batch (`runEnrichment` in `main.go`) merge-sorts events and alerts into one true chronological sequence before feeding the `Tracker` — processing all events, then all alerts, would let a later alert's cooldown wrongly suppress an earlier event's trigger, since `fire()`'s cooldown check is timestamp-based, not call-order-based; live (`runFollow`) calls `ObserveEvent`/`ObserveAlert` inline since events already arrive in real order one at a time. Gated by `-quiet-startup` the same as alert printing, for the same reason: a restarted long-running service shouldn't re-spend lookups (or reset repeat history) on the same historical data every restart.
- **Output**: `internal/output/cti.go` adds `ToCTILine` (human) and `ToCTIJSONLine` (tagged `"type":"cti"`, so a consumer piping `-follow -json` through `jq` can tell CTI notes apart from alert lines). CTI output always goes to **stderr**, never stdout, regardless of `-json` — stdout stays exactly what it's documented to be (the alert table/JSON/summary); enrichment is supplementary context about it, not part of the detection artifact.
- 13 new tests in `internal/counterintel` (repeat-threshold timing, window expiry, critical-severity firing, cooldown sharing across both trigger reasons — including one built from the real screenshot's exact timing — independent per-source tracking) and 3 in `internal/output`/`cti_test.go`. `gofmt`/`go vet`/`go test -race ./...` clean, 70 tests total.
- **Verified end-to-end against real data**: rebuilt the binary, fed it the exact three-line-burst fixture transcribed from the motivating screenshot (`195.178.110.217`, 90s apart) — confirmed **zero** brute-force alerts (correctly below the burst threshold) but a real `[CTI]` line with genuine RDAP/GeoIP data (`TECHOFF_SRV_LIMITED`, Andorra la Vella) triggered by `repeat_offender`, both in table and `-json` mode. Also fed a real 21-attempt critical-severity burst (TEST-NET-3 IP) and confirmed the repeat trigger correctly fires first (chronologically earlier, at the 3rd event) and the shared cooldown correctly suppresses the redundant severity trigger once the burst alert is processed. Reran the full vendored loghub dataset without `-cti` to confirm the wiring caused no regression (still exactly 327 alerts).
- **Not verified**: a live `-follow -cti` smoke test. Base (non-CTI) live alerting also produced no output under repeated attempts in this session's sandboxed shell — appended lines were confirmed on disk afterward but `fsnotify` never delivered the corresponding events to the running process, while `go test`'s own `internal/tail` tests (writes from within the same Go process) passed normally. Looks like an environment/sandbox limitation on cross-process inotify delivery, not a code bug — same category of "can't fully verify inside this shell" as the honeypot's own real `-follow` testing having always been done in a real terminal or on the droplet itself, per its own history above. Worth a quick real-terminal or droplet smoke test before trusting `-cti` in production; the live-mode wiring is a minimal, unit-tested addition to the already-proven `live.Feed` call site.
